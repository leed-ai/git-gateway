## 0.1.3

### Patch Changes

- [#25](https://github.com/leed-ai/git-gateway/pull/25) [`5c855c8`](https://github.com/leed-ai/git-gateway/commit/5c855c89993f30604072af140641ba68b144ebae) Thanks [@kingmesal](https://github.com/kingmesal)! - Type-checks against `@types/node` 26, whose Web Crypto and Web Streams types take only bytes over an `ArrayBuffer`. `sha1Bytes` and `deflate`/`inflate` in core, and `sha1Hex` in the contract's reference gateway, still accept any `Uint8Array` and pass it through unchanged; an array over shared memory, which those APIs refuse, is now copied first. The new `arrayBufferBacked` helper (in `core/bytes` and `contract/reference/bytes`) does that. `DecodedJwt.signingInput` and `signature` in auth-jwt, and `decodeBase64Url`'s result, are now typed `Uint8Array<ArrayBuffer>`, which they always were.

- [#25](https://github.com/leed-ai/git-gateway/pull/25) [`5c855c8`](https://github.com/leed-ai/git-gateway/commit/5c855c89993f30604072af140641ba68b144ebae) Thanks [@kingmesal](https://github.com/kingmesal)! - The `zod` peer dependency now requires 4.6.0 or later (`^4.6.0`, was `^4`). Older 4.x releases do not behave as the published contract says: before 4.5.0 a commit action refused for invalid base64 `content` reports the issue with an empty path instead of naming the `content` field, and the generated JSON Schema differs (including a `FilePath` pattern that no longer gives the same verdict as the schema); before 4.6.0 `z.toJSONSchema` emits a different email pattern, so the generated JSON Schema still differs from the one published. `hono` (`^4`) and `cloudflare` (`^5`) are unchanged; their lowest versions pass the whole suite.

## 0.1.2

### Patch Changes

- [#23](https://github.com/leed-ai/git-gateway/pull/23) [`29c5507`](https://github.com/leed-ai/git-gateway/commit/29c5507ec5426477fd64a0f6df2ccaac19ec3e36) Thanks [@kingmesal](https://github.com/kingmesal)! - No storage read is made while a receive-pack to the storage host is open. A push with fast-forwards to prove from its pack, or whose push policy asks for changed paths, used to stream to the host while the gateway read the repository with the pack checksum held back; a host that serialises per repository (the Artifacts local simulator in Wrangler 4.165+ locks a repository for the whole of each request) made those reads wait on the gateway's own push, and the push hung. Such a push is now read whole, proven and checked first, and only then sent to the host; a refusal sends nothing to storage. A push with nothing left to check still streams.
  
  New `SmartHttpConfig.maxFastForwardPackBytes` (default 32 MiB) bounds the pack held for a fast-forward proof. A larger push still streams, with its checksum held back, but is proven from the pack alone, so an update whose proof needs commits from storage is refused as unverifiable. `maxVerdictWaitMs` now applies only to such a streamed push. `holdPush` joins `guardPush` in `proxy/push-guard`, and `guardPush` can resume a scan.

## 0.1.1

### Patch Changes

- [#20](https://github.com/leed-ai/git-gateway/pull/20) [`b24d579`](https://github.com/leed-ai/git-gateway/commit/b24d5794077ba417f96ad253ec27c2e624829deb) Thanks [@kingmesal](https://github.com/kingmesal)! - Reading an id as the wrong kind of object is `null` on Cloudflare Artifacts, as the `StorageBackend` contract requires. The live binding refuses `readTree` of a blob (and similar reads) with an error whose code does not survive, only the message "Invalid object requested. SHA must identify a commit or a tree. <sha> is a blob."; the backend surfaced that as `storage_unavailable`, so any push whose thin pack deltas against an existing blob was refused as "the push could not be checked". `readCommit`, `readTree`, `readBlob` and `readFile` now map exactly that refusal to `null` (by its message, or by probing the other kinds when an `INTERNAL_ERROR` or code-less error does not say), and every other failure still surfaces. The contract now spells the rule out on `readCommit`, `readTree` and `readBlob`, and the backend contract suite gains a case reading an object by asking for each kind in turn.

## 0.1.0

### Minor Changes

- [#1](https://github.com/leed-ai/git-gateway/pull/1) [`eeb1c3f`](https://github.com/leed-ai/git-gateway/commit/eeb1c3fe8185f39453291583886b66b629af5efe) Thanks [@kingmesal](https://github.com/kingmesal)! - Freeze the RPC contract: Zod schemas for every RPC input and output, commit action, ref update, tree entry, commit, error and configuration object; the `GitGateway` interface; an in-memory reference implementation; and the implementation-agnostic behaviour suite (`registerBehaviourSuite`). From the first `next` publish on, changing a contract schema is a breaking change.

- [#1](https://github.com/leed-ai/git-gateway/pull/1) [`eeb1c3f`](https://github.com/leed-ai/git-gateway/commit/eeb1c3fe8185f39453291583886b66b629af5efe) Thanks [@kingmesal](https://github.com/kingmesal)! - `SmartHttpConfig.deniedStatus` (`'err'`, the default, or `403`) chooses how the smart-HTTP proxy answers an authorization refusal: in-protocol with an `ERR` packet as before, or HTTP 403 with the reason as a plain-text body, which git reports as "The requested URL returned error: 403". Branch-policy refusals stay in-protocol either way.

- [#7](https://github.com/leed-ai/git-gateway/pull/7) [`6c76ff1`](https://github.com/leed-ai/git-gateway/commit/6c76ff1687feb0da848b9795c67eaf7ecc77d7ac) Thanks [@kingmesal](https://github.com/kingmesal)! - A non-fast-forward push to a fast-forward-only branch is now always refused in-protocol (`ng <ref> <reason>`), even when the storage host gives up on the deliberately truncated pack before the gateway has recorded its verdict; it used to be answered 502 "storage host unreachable". `SmartHttpConfig.maxVerdictWaitMs` (default 60000) bounds that wait; genuine storage failures are still 502 and nothing is written.
  
  `StorageBackend` gains an optional capability, `isAncestor(repo, ancestor, descendant): Promise<boolean | null>`. The proxy proves fast-forwards with it (one call per commit where the pushed pack meets storage) and falls back to the `readCommit` walk when a backend lacks it. `GitLabBackend` implements it with the merge-base API and `MemoryBackend` in memory; the backend contract suite checks it for backends that offer it. Artifacts has no equivalent call and keeps the walk.

- [#11](https://github.com/leed-ai/git-gateway/pull/11) [`16bcfd1`](https://github.com/leed-ai/git-gateway/commit/16bcfd1f7539cbbcfdf74cc0968de477527064c2) Thanks [@kingmesal](https://github.com/kingmesal)! - An optional `PushPolicy` hook (`GatewayAppOptions.pushPolicy`) runs after the branch policy on every push and can refuse updates in-protocol for what they change. `needs()` decides per push whether `check()` gets changed paths: the commits each update brings with every `ChangedPath` (path, change, modes, ids, size), computed from the pushed pack and storage within new bounds (`SmartHttpConfig.maxPushPolicyPackBytes`, `maxPushPolicyObjectBytes`, `maxPushPolicyReads`, `maxChangedPaths`); a push that cannot be checked within them is refused. New schemas: `ChangedPath`, `PushedCommit`, `PushPolicyUpdate`, `PushPolicyInput`, `PushPolicyNeeds`, `PushRefDecision`, `PushPolicyResult`. Core's `readPack` gains `maxObjectBytes`, and `deltaResultSize` is exported from `pack/apply-delta`.

- [#1](https://github.com/leed-ai/git-gateway/pull/1) [`eeb1c3f`](https://github.com/leed-ai/git-gateway/commit/eeb1c3fe8185f39453291583886b66b629af5efe) Thanks [@kingmesal](https://github.com/kingmesal)! - Add the smart-HTTP proxy. The contract gains the proxy hooks (`Authenticator`, `Authorizer`, `BranchPolicy`, `AuditHook`) and their self-described schemas (`Principal`, `RefPattern`, `BranchRule`, `BranchPolicyConfig`, `PolicyResult`, `AuditEvent`, `SmartHttpConfig`), plus `readCredential` (the HTTP Basic password as a bearer credential). Core gains a streaming zlib inflater and `PackScanner`, which walks a pack as it streams past and collects its commits without buffering it, and `parseReceivePackRequest` now reports where the pack starts. The worker gains `createGatewayApp` (Hono routes for `/<repo>.git/info/refs`, `git-upload-pack` and `git-receive-pack`, with authentication, authorization and branch policy as middleware, per-request upstream credentials, streamed bodies, a decision cache, audit events and request-id logging), `RuleBranchPolicy` and `createGatewayWorker`. Fast-forward-only updates are proven from storage or from the pushed pack while it streams, holding back the pack checksum until they are. The new `JwtAuthenticator` verifies JWTs against an issuer's JWKS (OIDC discovery, key rotation, RS/PS/ES/EdDSA). The testkit gains `GitSandbox` and `serveStreaming` for driving the git binary against a streaming gateway.

- [#1](https://github.com/leed-ai/git-gateway/pull/1) [`eeb1c3f`](https://github.com/leed-ai/git-gateway/commit/eeb1c3fe8185f39453291583886b66b629af5efe) Thanks [@kingmesal](https://github.com/kingmesal)! - Add the storage backend layer. The contract gains the `StorageBackend` interface and its self-described schemas (`StorageRepoInfo`, `StorageTreeEntry`, `StorageRef`, `StorageLogOptions`, `GitAccess`, `GitRemote`) with shared input parsing and error helpers. Core gains a pack reader (OFS and REF deltas, thin packs, a pure-JS zlib inflater that reports stream ends), ref-advertisement and upload-pack codecs, a `fetch`-based smart-HTTP client, and an `invalid_pack` error. The testkit gains `MemoryBackend` (the full contract with a real protocol v0/v1 smart-HTTP server: shallow, partial-clone filters, thin packs, atomic pushes) and the backend contract suite every backend runs unchanged. New backends: `ArtifactsBackend` over the Workers binding, with `ArtifactsRestControl` over the `cloudflare` SDK outside Workers; and `GitLabBackend` over REST API v4 and git smart HTTP.
